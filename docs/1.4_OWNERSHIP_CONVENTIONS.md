# 1.4. Владение ресурсами и данными

Результат пункта **1.4** из [плана рефакторинга](../REFACTORING_PLAN.md).
Статус: подготовлено для ревью. Документ задаёт целевой контракт для

наблюдения о текущем коде относятся к коммиту
`6a298e4ac64201c23ad454657772fefd5d1ada71`.

Соглашения о пространствах и единицах находятся в документах
[1.2](1.2_COORDINATE_CONVENTIONS.md) и [1.3](1.3_UNITS_CONVENTIONS.md).
Здесь определяется, кто освобождает ресурс, какие данные копируются и какие
изменения разрешены через переданную или возвращённую ссылку.

## 1. Владелец, заимствование и передача

У освобождаемого ресурса **один ответственный владелец**. Остальные потребители
заимствуют его. Число ссылок на объект и включение в сцену сами по себе не
меняют владельца и не вводят подсчёт ссылок.

| Режим | Обязанность |
| --- | --- |
| Создание для внутренних нужд объекта | Объект освобождает ресурс при завершении работы и при неудачной инициализации |
| Фабрика возвращает созданный ресурс | После успешного возврата владельцем становится вызывающий код |
| Переданный готовый ресурс | По умолчанию заимствуется; получатель не вызывает его `dispose()` |
| Явная передача владения | Получатель принимает обязанность освобождения; прежний владелец её больше не выполняет |
| Копирование значения | Получатель хранит независимые данные; исходный объект остаётся у вызывающего кода |
| Выходной параметр | Метод может записывать в него в пределах описанного контракта, но не удерживает после вызова |

Передача владения должна быть видна в имени операции или именованном параметре,
например `takeOwnership`. Точные сигнатуры вводятся вместе с реализацией.
Она вступает в силу только после успешного принятия ресурса; при ошибке
переданный извне ресурс остаётся у прежнего владельца. Нельзя одновременно
передать один ресурс двум владельцам. Заимствующие потребители должны закончить
работу до освобождения ресурса его владельцем.

Ресурс относится к WebGL-контексту, в котором создан. Высокоуровневый API
проверяет совместимость контекстов и состояние ресурса перед подключением.
Сырые `Gl*` handles остаются низкоуровневой границей: без обёртки библиотека
не может гарантировать обнаружение внешнего удаления или двойной передачи.
При прямой работе с handle эти обязанности лежат на вызывающем коде.

| `Camera`, `Transform`, `Projection` | Математическое состояние и кэши | Контекст родительского преобразования, если нужен; GPU-ресурсов нет |
| `CameraUniforms` | Свои значения для текущего снимка камеры | Камера |

| `CanvasViewport` | Наблюдатели размера, подписки и собственные запланированные callbacks | Canvas, камера, контекст и проход рендера |

| `BoneVisualizer` | Созданный меш и рабочая поза скелета | Переданные программа, материал, данные скелета и клипа |

`ChronosGL.create*()`, `RenderProgram.makeMeshData()`, `shape*`, загрузка
геометрии и фабрики визуализирующих мешей возвращают ресурс вызывающему коду.
Наличие метода-фабрики на программе не означает, что программа владеет всеми
созданными через неё мешами. Удаление программы не удаляет совместимый меш.

`ShadowMap.getMapTexture()` возвращает **заимствованную** текстуру. Её владельцем
остаётся framebuffer карты теней, а `ShadowMap` владеет этим framebuffer.
Это цепочка владельцев без второго вызова `dispose()` для той же текстуры.
Готовая texture может использоваться многими материалами; удаление материала
не удаляет texture. Аналогично удаление узла из одной ветви DAG не уничтожает
узел, меш или материал, которые используются другой ветвью.

`remove()` и `clear()` у списков сцены удаляют связи. Рекурсивное освобождение
общего графа через эти методы не допускается. Общими GPU-ресурсами владеет
приложение или явно созданный объект-владелец. Для обычных CPU-контейнеров
без подписок и внешних ресурсов отдельный `dispose()` не обязателен.

## 3. Освобождение, замена и ошибки создания

### Контракт `dispose()`

Первый вызов сразу помечает объект неактивным, прекращает его callbacks и
освобождает только собственные ресурсы. Повторный вызов безопасен: повторных
удалений и повторной отмены тех же подписок нет. Ссылки на собственные handles
и крупные CPU-данные очищаются; заимствованные объекты освобождать нельзя.

Для GPU-обёрток освобождение имеет синхронный интерфейс `void dispose()`.
Это завершение работы обёртки и отправка операций удаления, а не ожидание
окончания исполнения GPU-команд. Для владельцев `StreamSubscription` и иной
асинхронной очистки используется `Future<void> dispose()`: объект становится
неактивным сразу, завершение Future означает окончание очистки. Повторные вызовы
возвращают тот же Future, включая незавершённую очистку.

После начала освобождения методы использования (`draw`, `activate`, `update`,
загрузка данных, получение действующего handle) выдают `StateError` до обращения
к WebGL. Разрешены повторный `dispose()`, `isDisposed` и чтение диагностических
метаданных, например имени. Уже поставленные в очередь внутренние callbacks
после отключения просто завершаются без изменения состояния и `preventDefault()`.
CPU-снимки, ранее переданные вызывающему коду, остаются его данными.
Перед использованием заимствованных обёрток потребитель также проверяет их
состояние: освобождённая зависимость приводит к `StateError`, а не к вызову WebGL
с недействующим ресурсом. Для сырых handles действует оговорённая выше граница.

Порядок очистки владельца: отключить источники работы, убрать внутренние ссылки
потребителей, освободить контейнеры GPU-состояния и собственные зависимости.
При ошибке очистки одного элемента попытки очистить остальные продолжаются;
ошибка сообщается после них. Владелец не возвращается в рабочее состояние.
Для составного объекта завершение асинхронной очистки включает его собственные
дочерние владельцы, но не заимствованные зависимости.

Удаление обёртки экрана не удаляет canvas и не теряет WebGL-контекст.
Автоматическое восстановление ресурсов после потери контекста этим пунктом
не вводится; `dispose()` должен быть допустим и для уже недоступного контекста.
Сборщик мусора и finalizers не заменяют явное освобождение.

### Буферы и attachments

При замене ресурса сначала проверяются аргументы и готовится новое состояние.
После успешного переключения старый собственный ресурс освобождается, старый
заимствованный — только отключается. Если подготовка не удалась, временные
ресурсы удаляются, прежняя рабочая конфигурация сохраняется, переданное извне
владение не принимается.

Один handle может встречаться в нескольких слотах одного владельца. Учёт ведётся
по идентичности ресурса, а не по числу слотов: собственный буфер нельзя удалить
при замене одного атрибута, пока он нужен другому атрибуту этого же меша.
При окончательной очистке каждый собственный handle удаляется один раз.
Переустановка того же handle не удаляет его и не меняет режим владения скрыто.
Смена владельца — отдельная операция с явным отсоединением прежнего владельца.

`MeshData.clearData()`, если сохраняется в API, оставляет **пустой пригодный
к повторному заполнению меш**: освобождает собственные буферы, отключает внешние,
очищает VAO-привязки, CPU-данные, количества индексов/экземпляров и тип индексов.
`dispose()` завершает жизнь меша и освобождает также VAO.

Сейчас [`clearData()`](../lib/src/core/mesh_data.dart#L81) удаляет все буферы
без различения владения, не сбрасывает их записи и не удаляет VAO.
[`changeAttributeBuffer()`](../lib/src/core/mesh_data.dart#L137) перезаписывает
старый handle без очистки; повторные `addVertices()`, `addAttribute()` и
`addFaces()` также создают новые handles. Пункт 2.2 должен покрыть эти пути
и использование одного буфера несколькими атрибутами.

У framebuffer текстуры-attachments имеют независимый жизненный цикл.
Публичная замена поля `colorTexture` не должна оставлять GPU attachment старым:
целевой API меняет и проверяет конфигурацию целиком, включая размеры, контекст,
полноту и режим владения. При resize внутренние attachments заменяются
по тому же правилу; заимствованные текстуры не пересоздаются за их владельца.
`Framebuffer.screen()` и `defaultFramebuffer()` не синонимы: в текущем коде
вторая фабрика создаёт отдельную offscreen-цель с двумя текстурами.

### Частично созданные объекты

| Место ошибки | Что очищается |
| --- | --- |
| Компиляция vertex/fragment shader или линковка | Все уже созданные временные shader handles и незавершённая программа |
| Успешная линковка | Временные shader handles отсоединяются и удаляются; программа остаётся у результата |
| Инициализация `RenderProgram` после линковки | Созданная программа, если получение метаданных или другая инициализация завершилась ошибкой |
| Загрузка части меша или текстуры | Все handles, созданные неудачным конструктором/фабрикой |
| Создание framebuffer из переданных текстур | Новый framebuffer handle; переданные текстуры остаются у вызывающего кода |
| Фабрика framebuffer с собственными текстурами | Новый framebuffer и все уже созданные этой фабрикой текстуры, включая сбой создания следующей текстуры |
| Составной helper/визуализатор | Все успешно созданные до ошибки собственные ресурсы в обратном порядке зависимостей |
| Подключение части обработчиков | Уже подключённые этим объектом обработчики и наблюдатели |

Очистка ошибки не должна затереть исходную ошибку создания. Для временно
изменённых bindings сохраняется и восстанавливается предыдущее состояние,
если это требуется контрактом данной операции; операции очистки не оставляют
удалённый handle текущей рабочей зависимостью владельца.

Сейчас [`compileWholeProgram()`](../lib/src/core/chronosgl.dart#L136) и
`_compileShader()` не удаляют созданные handles на этих путях.
[`Framebuffer`](../lib/src/core/framebuffer.dart#L66) выбрасывает ошибку
неполноты после создания handle без очистки. Общего публичного `dispose()`
у GPU-обёрток пока нет; `ChronosGL` предоставляет только `deleteBuffer()`.
Нужны парные операции удаления для уже создаваемых VAO, textures, framebuffer,
programs, shaders, samplers и transform feedback; их добавление — пункт 2.1.

## 4. Подписки, браузерные источники и помощники

Создавший подписку сохраняет её и отменяет при `dispose()`. Для
`addEventListener` сохраняются точный callback, target, тип и параметры,
нужные для удаления; новое замыкание не заменяет исходный callback.
Наблюдатель resize отключается владельцем, запланированный им callback
отменяется, а запоздавший результат проверяет состояние владельца.

`disable()` контроллера — обратимое прекращение управления; `dispose()` —
окончательное освобождение. В отключённом состоянии обработчики контроллера
не меняют камеру и не подавляют стандартное поведение DOM-событий. Собственное
состояние удерживаемых клавиш, кнопок и накопленных дельт сбрасывается; повторное
включение не применяет старый ввод. Повторное включение не дублирует подписки.
Потеря фокуса также сбрасывает собственное состояние удержания.

Если `Keyboard`/`Mouse` переданы контроллеру, он их заимствует: отключение или
удаление контроллера не отменяет их общие подписки и не очищает состояние других
потребителей. При совместном использовании ввода нужен снимок кадра или
отдельный курсор потребления для каждого контроллера. Вызов общего
`afterFrameCleanup()` одним потребителем не может быть скрытой частью такого
контракта. Устройство ввода освобождает его внешний владелец после потребителей.

Сейчас [`Keyboard` и `Mouse`](../lib/src/webhelper/input.dart) не сохраняют
подписки; callback колеса создаётся без поля для последующего удаления.
[`OrbitCamera`](../lib/src/webhelper/interactive_camera.dart#L9) создаёт оба
устройства, а оба [`*ResizeAware`](../lib/src/misc/example_helper.dart#L241)
не сохраняют подписку resize. Это пути для пунктов 2.7 и 4.2–4.8.

DOM-элемент, переданный в `ImageTexture`, заимствуется. Освобождение текстуры
удаляет GPU-ресурс и снимает удерживаемую ссылку, но не удаляет элемент, не
останавливает чужое видео и не закрывает чужой `ImageBitmap`/media stream.
Созданный самой фабрикой временный источник освобождается этой фабрикой,
когда больше не нужен. Для обновляемой текстуры источник сохраняется до
завершения обновлений; его срок жизни должен быть указан в API.

[`loadImage()` / `loadVideo()`](../lib/src/webhelper/http_request.dart#L47)
передают созданный элемент вызывающему коду после успешного завершения.
Временные listeners загрузчика снимаются и при успехе, и при ошибке; текущий
`_waitForLoadEvent()` это уже делает. Эти функции возвращают `Future`, публичной
отмены загрузки сейчас нет — `dispose()` другого объекта её не добавляет.
Если асинхронный результат пришёл после удаления потребителя, потребитель
не устанавливает его в своё состояние, а освобождает полученный собственный
результат. Заимствованные результаты чужих операций он не уничтожает.

[`makeVideoElementFromCamera()`](../lib/src/webhelper/webtexture.dart#L3)
после успеха передаёт вызывающему коду ответственность за созданный видеоэлемент
и stream. Завершение использования требует остановить созданные media tracks
и отсоединить stream от элемента. На ошибке функция уже останавливает полученные
tracks. Для нового возвращаемого объекта-владельца эта обязанность входит
в его `dispose()`; простая упаковка элемента в texture не передаёт stream texture.

Диагностическая панель удаляет только собственные DOM-узлы. Для оформления
используется собственная обёртка, чтобы не переписывать оформление чужого root
и затем не восстанавливать поверх изменений приложения устаревшие стили.
Визуализатор карты теней заимствует depth texture: отдельный sampler либо
восстановление реально прежних параметров через `finally` предотвращает порчу
настроек карты при ошибке отрисовки. Сейчас
[`ShadowMap.visualize()`](../lib/src/misc/shadowmap.dart) меняет параметры общей
texture и восстанавливает фиксированные значения только при обычном выходе.

## 5. Коллекции и изменяемые значения

### Копирование контейнера и его элементов

`final List` защищает ссылку поля, но не элементы. Read-only map или list
также не делает неизменяемыми содержащиеся в нём `Vector3`, `Matrix4` или
`TypedData`. Поэтому для каждой границы выбирается один из следующих контрактов.

| Граница API | Целевое правило |
| --- | --- |
| Списки узлов, batch и групп uniforms в конструкторах/`addAll` | Копируется структура списка; сами узлы и группы заимствуются по ссылке |
| Публичное чтение `children`, `nodes`, списков batch/uniforms | Структурно неизменяемый снимок; изменение членства через методы владельца |
| `draw(..., uniforms)` | Список и пользовательские группы только читаются; временные transforms/materials хранятся отдельно |
| `draw(..., stats)` | Явный выходной список: в него добавляются результаты; существующие записи не удаляются |
| Uniform — число, вектор, матрица, список флагов или numeric typed array | Setter сохраняет независимое значение, включая копию изменяемых элементов |
| Uniform — texture/ресурс | Хранится заимствованная ссылка; копирования GPU-ресурса и передачи владения нет |
| `UniformGroup.getUniforms()` | Снимок map и изменяемых значений; ресурсные ссылки остаются заимствованными |
| `Transform`/`Camera`: входные векторы и матрицы | Копируются; изменение входного объекта после setter не меняет позу |
| Getters позы, матриц, размеров | Независимый снимок либо явно названный `copy...Into(out)`; внутренний scratch не возвращается |
| Загрузка CPU-данных в `GpuMesh` | Вход читается; сохраняемая CPU-копия независима от входа; GPU изменяется только явной загрузкой |
| Чтение CPU-данных из `GpuMesh` | Снимок; изменение результата не меняет кэш и не загружает данные на GPU |
| Загрузка pixels в texture | Входные bytes читаются без удержания после синхронной загрузки; асинхронный вариант обязан фиксировать срок заимствования отдельно |
| `flatten*`, `readPixels`/`extract*`, `getArrayBuffer` с `out`/`buf` | Переданный выход заполняется; не удерживается; возвращается тот же буфер, если метод возвращает результат |
| Те же функции без выходного буфера | Создают и возвращают новый буфер вызывающему коду |
| Метаданные `ShaderObject` при создании программы/меша | Снимок строк, списков и map раскладки; последующая правка builder не меняет скомпилированную программу |
| `TextureProperties`, blend/stencil presets, цвета | Неизменяемые значения; до перехода — независимые копии при принятии настроек |

Снимок структуры не клонирует сцену: изменение самого узла или `UniformGroup`
остаётся видимым его потребителям. Владение ресурсом и право изменять числовые
данные различаются. Редактирование структуры графа во время обхода не входит
в поддерживаемый контракт; изменения применяются между проходами.

Для производительных путей допускается отдельный явно названный API чтения
по ссылке/записи в `out`. У него документируется срок действия ссылки и разрешённые
мутации. Обычный getter не выдаёт скрыто переиспользуемый временный объект.
Рендер может использовать собственные scratch-матрицы внутри одного синхронного
draw, не публикуя их как долгоживущие значения. Противоречащие контракту алиасы
входа и `out` отклоняются либо прямо поддерживаются конкретным методом.

Сейчас [`UniformGroup`](../lib/src/core/abstractions.dart#L28) сохраняет значения
по ссылке и возвращает внутреннюю map. [`Spatial.getPos()`](../lib/src/core/spatial.dart#L36)
возвращает переиспользуемый `_pos`, а поле `transform` открыто для изменения.
[`MeshData`](../lib/src/core/mesh_data.dart#L90) удерживает переданные массивы
атрибутов и выдаёт их через `getAttribute()`. `ShaderObject.getAttributeLayoutMap()`
возвращает внутреннюю map, которую сохраняет меш. `Texture` удерживает исходный
объект properties; глобальные presets сейчас изменяемы.

В [пункте 1.9](1.9_SHARED_SETTINGS_AND_FRAME_RATE_REPRODUCTIONS.md) сохранены
воспроизведения влияния общих цветов, blend/stencil presets, texture properties
и материала `unitNode` на других потребителей. Их исправления остаются в фазе 6.

Переход setter uniforms к снимкам меняет существующий способ анимации через
изменение ранее переданного `Vector3`/`Matrix4`. В миграции требуется повторный
setter с новым значением либо отдельная явная привязка по ссылке, если такой API
будет добавлен. Нельзя изменить это поведение без описания для потребителей.
Зато общая texture остаётся общей по прежней ресурсной ссылке.

### Рисование и исключения

[`Scene`](../lib/src/scene/render_phase.dart#L12) сейчас сохраняет исходный
список uniforms. В [пункте 1.7](1.7_UNIFORMS_LIST_OWNERSHIP.md) исправлены
`RenderPhase.draw()` и `drawRecursively()`: служебные группы и материал собираются
отдельно, исходные список и группы сохраняются при успехе и исключении.
Поддерживаются также неизменяемые списки.

Пункт **1.7** устраняет изменение пользовательского списка уже на текущем
API: draw собирает свой рабочий набор, исходные список и группы сохраняются
при успехе и ошибке. Требуется и восстановление внутреннего временного состояния
обхода, чтобы следующий кадр не использовал остатки предыдущего. Изменение
выходного `stats` разрешено: записи успешно завершённых draw при последующей
ошибке могут остаться, полный откат статистики не обещается.
Это не контракт восстановления всего глобального состояния WebGL вокруг draw.

### CPU-builders и анимация

`GeometryBuilder` остаётся явно изменяемым редактором собственных CPU-данных.
Его рабочие коллекции можно редактировать по контракту builder; перед загрузкой
проверяются инварианты. Это отдельный контракт редактора; внутренние коллекции
GPU-обёртки остаются защищёнными от прямого изменения.

Обычные `addVertex/addVertices/addAttributesVector*` копируют значения.
Методы с `TakeOwnership` принимают сами изменяемые элементы без копирования:
вызывающий код больше не меняет эти элементы через прежние ссылки.
При `addVerticesTakeOwnership(list)` структура списка не передаётся — метод
добавляет ссылки на элементы в свой список и не удерживает исходный контейнер.
Сам список можно переиспользовать, но переданные векторы уже принадлежат builder.
Это соответствует различию существующих
[`addVertices` и `addVerticesTakeOwnership`](../lib/src/core/geometry_builder.dart#L281).

`mergeAndTakeOwnershipSimple(other)` переносит содержимое и оставляет `other`
пустым, пригодным к новому заполнению; ссылки на перенесённые элементы больше
не дают прежнему владельцу права изменять их. Проверки совместимости и запрет
слияния builder с самим собой выполняются до мутации обоих объектов.

Кость и клип копируют входные изменяемые матрицы, времена и значения ключей
при создании; runtime-данные клипа читаются без изменения. Идентичность костей
в скелете сохраняется: копирование не должно создавать несогласованные ссылки
в `BoneAnimation`. Импортёр возвращает созданные CPU-данные вызывающему коду
и не меняет исходный JSON. `AnimatedSkeleton` — явно изменяемый результат
вычисления позы, используемый как выходной параметр. Обновление позы не меняет
исходные ключи анимации и bind-матрицы. Существующий `recomputeLocalOffsets()`
явно изменяет данные скелета; в целевом API это операция подготовки до публикации
runtime-снимка, а не неявный шаг проигрывания.

| 2.1–2.4 | Парные create/delete, повторный dispose, использование после dispose, ошибки каждого шага создания и инициализации |
| 2.5–2.6 | Собственные/внешние буферы и attachments, замена тем же handle, несколько слотов одного handle, откат неудачной замены |

| 5.3, 5.6–5.8 | Удаление одной ветви DAG не удаляет общие ресурсы; CPU/GPU-копии и раскладка атрибутов независимы |

| 8.1–8.5 | Примеры показывают создание, совместное использование и освобождение в правильном порядке; таблица миграции актуальна |

Минимальные сценарии для реализации:

- Один внешний buffer подключён к двум мешам: удаление каждого меша удаляет
  его VAO, но не внешний buffer; владелец удаляет buffer после обоих потребителей.
- Один собственный buffer используется двумя атрибутами: замена одного слота
  его не удаляет, освобождение последнего использования удаляет ровно один раз.
- Framebuffer с внешними textures освобождается без удаления textures;
  фабричная цель освобождает свои attachments один раз, включая combined depth/stencil.
- Ошибка fragment shader после успешного vertex shader и ошибка инициализации
  `RenderProgram` после линковки не оставляют созданных handles.
- Две ветви DAG используют один меш и материал: удаление связи одной ветви
  сохраняет вторую. Замена texture в материале не удаляет прежнюю texture.
- После dispose/disable queued input/resize callbacks не меняют камеру,
  не подавляют события и не создают повторные подписки; заимствованный ввод жив.
- Изменение исходного списка, вектора, typed array или properties после setter
  не меняет сохранённый снимок; изменение выданного снимка не меняет владельца.
- Выходной буфер заполняется без скрытого удержания; TakeOwnership переносит
  только оговорённые данные; неизменяемый входной список не требуется менять.
- Ошибка визуализатора не портит sampling карты теней; удаление визуализатора
  сохраняет карту и внешние программу/материал.

Для проверки жизненного цикла нужны счётчики созданных/удалённых handles и
инъекция ошибок, а не только сравнение изображения. Для подписок — проверка
событий до отключения, после него и после повторного включения. Эти проверки
добавляются вместе с реализацией соответствующих пунктов; здесь они не объявляются
уже проходящими. Код библиотеки и тесты в пункте 1.4 не меняются.
