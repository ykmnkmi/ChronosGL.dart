# 3.7. Обновление матриц и владение возвращаемыми значениями

Пункт **3.7** [плана рефакторинга](../REFACTORING_PLAN.md) закрепляет единый
контракт доступа для математических `Camera`, `Transform` и `Projection`.
Матрицы и их `Float32List` принадлежат вызывающему коду: изменение результата
не меняет исходный объект, последующие изменения объекта не меняют старый
результат. Это изменяемые независимые снимки, а не read-only обёртки.

## Когда видны изменения

Успешный setter сразу меняет исходное состояние. Следующее чтение получает
актуальную матрицу; вызов `update()` и предварительное чтение других getters
не нужны. Камера хранит положение и нормализованную ориентацию, вычисляя
world/view/combined по запросу. Неизменяемая проекция хранит рассчитанную
матрицу внутри и выдаёт копии. `setProjection` заменяет значение целиком.

| Чтение | Значение и зависимости |
| --- | --- |
| `Camera.worldMatrix` | `C = T(eye) * R`, зависит только от позы |
| `Camera.viewMatrix` | `V = inverse(C)`, зависит только от позы |
| `Camera.projectionMatrix` | `P`, зависит только от проекции |
| `Camera.viewProjectionMatrix` | `P * V`, зависит от текущих позы и проекции |
| `Camera.worldPosition`, `worldRotation` | Независимые копии компонентов позы |
| `Transform.matrix` | Текущая local → parent матрица |
| `Projection.matrix` | Неизменяемая view → clip проекция |

Порядок чтения не меняет результат. Каждый снимок соответствует состоянию
в момент своего чтения: если между чтениями изменить камеру, старые и новые
снимки закономерно относятся к разным состояниям. Для одного кадра сначала
завершите изменения позы и проекции, затем читайте нужные значения.

Не требуется и обратная запись матрицы вида в позу. Чтобы изменить камеру,
используйте `setPosition`, `setPositionFromVector`, `setRotation`, `lookAt`
или `setProjection`. Для редактирования матрицы `Transform` явно передайте
изменённый снимок в `setMatrix`; этот метод также копирует входные данные.
`Projection` неизменяема, поэтому для новых параметров создаётся новое значение.

## Копирование в своё хранилище

Камера теперь предоставляет четыре метода:

```dart
camera.copyWorldMatrixInto(world);
camera.copyViewMatrixInto(view);
camera.copyProjectionMatrixInto(projection);
camera.copyViewProjectionMatrixInto(combined);
```

Как и существующие `Transform.copyMatrixInto(out)` и
`Projection.copyMatrixInto(out)`, они полностью записывают текущую матрицу
в хранилище вызывающего кода. Ссылка на `out` не сохраняется: его можно
повторно использовать, передать другим потребителям или изменить независимо.
Последующие setters не обновляют `out`; для обновления нужно повторить copy.
Предоставление выходного хранилища не гарантирует отсутствие промежуточных
аллокаций: камера использует тот же расчёт, что и getters.

```dart
final camera = PerspectiveCamera(near: 0.1, far: 100)
  ..setPosition(0, 0, 10);
final view = vm.Matrix4.zero();
camera.copyViewMatrixInto(view);
camera.setPosition(0, 0, 20);
// view всё ещё содержит перенос -10 по Z.
camera.copyViewMatrixInto(view);
// Теперь перенос равен -20 по Z.
view.storage.fillRange(0, 16, 0); // Камера по-прежнему в (0, 0, 20).
```

Если расчёт вида или `P * V` не представим конечными Float32, getter и
соответствующий copy дают `StateError`. Исходное состояние и выходная матрица
сохраняются; можно исправить позу или проекцию и повторить расчёт. Ошибка
доступа к проекции подкласса также не меняет выход и не мешает копировать
world/view. Контракт snapshot распространяется и на реализации абстрактных
`Camera.projectionMatrix` и `Projection.matrix`.

## Legacy-граница и защита от aliases

`Spatial.transform` остаётся явно изменяемой local → parent матрицей для
совместимости с существующими узлами и примерами. `getPos`, `getEyePosition`
и методы направлений возвращают переиспользуемые рабочие векторы, а старые
`Perspective`/`Orthographic.getUniforms()` — рабочие данные адаптера.
Эти legacy API не получают snapshot-контракт математических типов; для
сохранения результата нужны собственные копии. Переход к новому адаптеру
`CameraUniforms` остаётся пунктом 3.9.

`Spatial.getViewMatrix(out)` уже запрещал передавать сам `transform`.
Теперь проверяется пересечение диапазонов в общем буфере: другая `Matrix4`
с тем же `Float32List`, новый view этого буфера и частичное пересечение
также дают `ArgumentError` до записи. Так inverse не может незаметно заменить
позу через alias. Непересекающиеся диапазоны одного буфера допустимы.

Явный мост к legacy остаётся доступен:

```dart
camera.copyWorldMatrixInto(legacyCamera.transform);
legacyCamera.getViewMatrix(view);
```

Эта операция копирует позу один раз, не связывая объекты. Для нового состояния
нужно повторить копирование. У `Transform` аналогичный мост к `Node`:
`transform.copyMatrixInto(node.transform)`.

## Проверки

[`camera_matrix_access_test.dart`](../test/camera_matrix_access_test.dart)
содержит 11 математических тестов: порча снимков через typed-data view,
безопасность общей проекции, все изменения позы и проекции без `update`,
сохранение старых снимков, повторное использование выходов с ненулевым offset,
ошибки вида/combined/проекции без частичной записи и восстановление,
явная фиксация матрицы `Transform` с копированием входа.

[`camera_matrix_access_compatibility_test.dart`](../test/camera_matrix_access_compatibility_test.dart)
содержит 3 браузерных теста: aliases матрицы/списка/буфера, частичное пересечение
и непересекающиеся выходы, а также независимость нового и legacy API
после явного копирования. Оба файла включены в preset `all`.

```sh
dart analyze
dart test test/camera_matrix_access_test.dart
dart test -P all
dart test -P all -p golden_chrome -c dart2wasm
dart run build_runner build --output=example:build/example
dart run tool/goldens.dart --self-check
```

Результаты на Dart 3.14.0: анализ без замечаний; 11 математических тестов
проходят на VM, JavaScript и Wasm, все 3 legacy-проверки — на JavaScript и Wasm.
Полный VM/JavaScript-прогон — 479 тестов, прогон с Wasm — 477 тестов (preset
также запускает VM-наборы; два legacy DOM-теста предназначены только для JS).
Сборка примеров и тестовых bootstraps завершилась успешно. Rendering goldens
совпадают с существующими эталонами; self-check подтверждает обнаружение
намеренного изменения цвета. Эталонные изображения не обновлялись.
