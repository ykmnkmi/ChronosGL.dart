# 2.9. Сквозные проверки жизненного цикла сцены

Пункт **2.9** [плана рефакторинга](../REFACTORING_PLAN.md) завершает
проверки фазы 2. [Новый браузерный набор](../test/scene_lifecycle_test.dart)
проверяет совместную работу сцены, GPU-ресурсов и ввода через публичный API.
Он включён в preset `all` для JavaScript и Wasm.

## Что проверено

Шесть тестов дополняют проверки отдельных владельцев из пунктов 2.1–2.8:

| Сценарий | Проверяемый результат |
| --- | --- |
| Пять циклов создания, отрисовки и очистки с `Framebuffer.effect` | Каждый цикл рисует два узла с общим индексированным мешем и материалом; после явной очистки нет живых ресурсов этого цикла |
| Те же циклы с `Framebuffer.defaultFramebuffer` | Дополнительно освобождается собственная depth-текстура framebuffer |
| Повторный `Scene.remove(node)` | Оставшийся узел продолжает использовать общий меш, материал и sampler; удалённый узел можно добавить обратно |
| Повторный `Scene.removeAll()` | Тот же узел в другой сцене остаётся пригодным к отрисовке |
| Удаление дочерней связи в DAG | Общий узел продолжает рисоваться через другую ветвь; восстановление связи возвращает второй draw |
| Очистка одного из двух потребителей | Удаление программы и framebuffer первой сцены сохраняет общий меш, материал, sampler и заимствованную текстуру результата для второй сцены |

В циклических сценариях каждый сеанс создаёт новые `Keyboard` и `Mouse`
на одном canvas. Все шесть типов событий сначала проверяются на активных
устройствах. После начала `dispose()` и после завершения возвращённых Future
состояние остаётся пустым, события не подавляются через `preventDefault()`.
Повторные вызовы возвращают прежние Future. Следующий сеанс получает ввод
с ожидаемыми дельтами, а все сохранённые устройства предыдущих сеансов
остаются неактивными.

Проверки общих ресурсов сравнивают число draw и фактические RGBA pixels.
После удаления потребителя изменение общей ссылки на sampler в материале
или обновление содержимого текстуры меняет результат оставшейся отрисовки.
Это проверяет дальнейшую работоспособность, включая чтение общего материала.

## Как проверяется освобождение

Инструментированный `ChronosGL` записывает каждый созданный и удалённый
buffer, VAO, texture, program, shader и framebuffer. После каждого цикла
проверяются количество выделений и соответствие удалений всем созданным handles:
каждый handle удалён ровно один раз. Повторно вызывается `dispose()` всех
GPU-владельцев, включая уже освобождённые framebuffer attachments.

Дополнительно настоящие WebGL-запросы `isBuffer`, `isVertexArray`, `isTexture`,
`isProgram`, `isShader`, `isFramebuffer` подтверждают удаление объектов.
Перед итоговым запросом программа снимается с текущего binding: WebGL может
откладывать физическое удаление используемой программы. Проверяется отсутствие
ошибок WebGL и сохранность контекста. Потеря контекста применяется только
в завершающем test teardown, после всех проверок; между циклами контекст общий.

Это проверка баланса выделений и запросов удаления, а не измерение памяти
GPU или сроков работы сборщика мусора браузера.

## Завершение сцены и границы API

Ресурсами тестового сеанса владеет вызывающий код. Порядок завершения:

1. Прекратить работу кадров и отключить устройства ввода.
2. Удалить связи сцены с узлами через `removeAll()`; при необходимости очистить
   принадлежащие приложению списки дочерних связей.
3. Явно освободить framebuffer, меши, программы и текстуры, которыми владеет
   приложение, после завершения работы всех их потребителей.
4. Дождаться завершения Future отключения ввода.

`Scene`, `Node`, `Material` и `RenderPhase` не получают новых методов
`dispose()`. Удаление узла или связи не передаёт владение ресурсами и не
освобождает их автоматически. Material заимствует текстуры uniforms.
В тестах общий framebuffer attachment освобождается внешним владельцем
после обоих framebuffer, а attachments фабричного framebuffer — самим
framebuffer. Вопросы новой структуры графа остаются в фазе 5.

## Покрытие критериев готовности фазы 2

| Критерий | Свидетельство |
| --- | --- |
| Многократное создание и уничтожение сцены с явной очисткой ресурсов | Два циклических сценария нового набора, общий контекст, контроль handles и ввода после каждого сеанса |
| Удаление узла сохраняет общий меш и материал | Три сценария удаления связей, pixels после удаления и изменения материала, восстановление связи |
| Повторный dispose и ошибки создания соблюдают контракт | Новый сквозной набор и проходящие специализированные наборы ниже |

Подробные проверки частичного создания и ошибок очистки остаются в
[2.4](2.4_RESOURCE_CREATION_FAILURES.md), передачи владения — в
[2.5](2.5_RESOURCE_OWNERSHIP.md), отката замены — в
[2.6](2.6_RESOURCE_REPLACEMENT.md). Повторное и повторно входящее освобождение
мешей проверяется в [2.2](2.2_MESH_DISPOSAL.md), остальных GPU-обёрток —
в [2.3](2.3_GPU_RESOURCE_DISPOSAL.md). Точное снятие callbacks, ошибки снятия
и запоздалая доставка проверяются в [2.7](2.7_INPUT_DISPOSAL.md), а ранний
отказ использования освобождённых объектов — в [2.8](2.8_DISPOSED_USAGE.md).

## Запуск

```sh
dart analyze
dart test -P all
dart test -P all -p golden_chrome -c dart2wasm
dart run build_runner build --output=example:build/example
```

Только новые сценарии:

```sh
dart test -p golden_chrome test/scene_lifecycle_test.dart
dart test -p golden_chrome -c dart2wasm test/scene_lifecycle_test.dart
```

Проверено на Dart 3.13.7: все шесть новых тестов проходят в JavaScript и Wasm.
Полный VM/JavaScript-набор — 279 тестов, VM/Wasm-набор — 277 тестов,
включая эталонные изображения; все проходят. `dart analyze` — без замечаний,
сборка примеров и тестовых загрузчиков через `build_runner` завершилась успешно.
Форматирование нового Dart-файла и `git diff --check` проверены.
Hot reload запрошен через Dart Tooling Daemon, но недоступен:
к найденному DTD не подключено запущенное приложение.
