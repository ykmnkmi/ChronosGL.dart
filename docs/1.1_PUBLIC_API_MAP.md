# 1.1. Карта публичного API ChronosGL

Результат пункта **1.1** из [плана рефакторинга](../REFACTORING_PLAN.md).
Статус: подготовлено для ревью. Будущие имена и модули ниже — предложения;
переименования, переносы и изменения экспорта ещё не выполнены.

## Область инвентаризации

Исходная точка — [lib/chronosgl.dart](../lib/chronosgl.dart), состояние исходников
на коммите `6a298e4ac64201c23ad454657772fefd5d1ada71`.
Проверены все девять экспортируемых библиотек и их `part`-файлы:
`core`, `shape`, `polygon`, `shader`, `importer`, `animation`, `webhelper`, `misc`,
`scene`. Импорты зависимостей сами по себе не считаются реэкспортами.

Через синтаксический разбор Dart обнаружены **953 публичных объявления верхнего
уровня** в 53 файлах с объявлениями: 53 класса, 11 typedef, 114 функций,
660 `const` и 115 переменных, включая `final`. Обход включает 63 файла вместе
с точками входа и файлами без действующих публичных объявлений.

[Полный перечень и индивидуальная карта всех 953 объявлений](1.1_PUBLIC_API_INVENTORY.md)
содержит исходный файл, строку, вид сущности, предлагаемое имя, модуль и действие.
Этот документ описывает основные решения и исключения для членов классов.
Полный снимок сигнатур, параметров и унаследованных членов в пункт 1.1 не входит;
контракты и изменения сигнатур уточняются в следующих пунктах плана.

Из перечня исключены приватные имена с `_`, локальные объявления, GLSL внутри
строк и закомментированный Dart. Поэтому `FlyingCamera`, `FPSCamera`,
`HemisphericalLight`, `LightConfig` и `createStandardShader` не считаются
существующим API. При этом `MidiInput` и `findBridge` являются действующими
публичными объявлениями, хотя их функциональность не реализована.

## Целевые модули

Имена `*.dart` в таблицах обозначают предлагаемые публичные точки входа
`package:chronosgl/<имя>`. Пути `src/...` обозначают внутреннюю реализацию,
которая не должна реэкспортироваться. Пути `example/...` обозначают код примеров.
Будущие пути не являются ссылками на уже существующие файлы.

| Точка входа | Содержание | Граница зависимостей |
| --- | --- | --- |
| `core.dart` | `NamedEntity`, `Transform`, `Color`, CPU-преобразования typed data, существующие функции логирования | Без DOM, WebGL и сцены |
| `geometry.dart` | `GeometryBuilder`, грани, генераторы форм, контуры, триангуляция и экструзия | CPU-данные; без GPU и DOM |
| `animation.dart` | Кости, скелеты, анимации и расчёт поз | CPU-данные; без GPU и DOM |
| `importers.dart` | Разбор Wavefront, ThreeJS JSON и Assimp JSON | Геометрия и анимация; загрузка по URL остаётся отдельно |
| `camera.dart` | Камеры и математические проекции | Использует `core`; без DOM, GPU-ресурсов и uniforms рендера |
| `shaders.dart` | `ShaderObject`, `ShaderVarDesc`, `ShaderStage`, канонические имена и GLSL | Описание шейдеров; компиляция на GPU остаётся в рендере |
| `webgl.dart` | `ChronosGL`, `Gl*`, числовые WebGL-константы | Низкоуровневая браузерная интеграция |
| `render.dart` | Программы, GPU-меши, загрузка геометрии, материалы, uniforms, текстуры, framebuffer, свет, полноэкранный проход | Использует CPU-модули и `webgl`; не зависит от примеров и диагностики |
| `scene.dart` | `Node`, `GroupNode`, `MeshNode`, `RenderBatch`, `RenderPass` | Организация объектов и проходов поверх рендера |
| `shadows.dart` | `ShadowMap` и шейдеры построения теней | Связывает свет, сцену и рендер; без обязательной визуализации |
| `web.dart` | Ввод, `OrbitControls`, `CanvasViewport`, загрузчики и браузерные источники текстур | DOM-интеграция с явно переданными объектами камеры и рендера |
| `debug.dart` | Панели статистики, визуализаторы костей, света и карт теней | Может использовать движок; движок не зависит от этого модуля |

`chronosgl.dart` остаётся общим импортом для поддерживаемого API движка.
Предлагается явно перечислять его экспорты из рабочих модулей, включая WebGL
и браузерные помощники для совместимости существующего способа использования.
Диагностика подключается отдельно через `debug.dart`; код примеров и внутренние
объявления в общий импорт не входят. Точный список переходных экспортов
реализуется и проверяется в фазе 7.

Внутренние модули должны импортировать конкретные зависимости, а не общий
`chronosgl.dart`. `CameraUniforms` принадлежит рендеру: математическая камера
не должна зависеть от `UniformGroup`. Отдельный `shadows.dart` позволяет
использовать сцену для теней, не создавая обратную зависимость базового рендера
от сцены. Разделение точек входа само по себе не делает CPU-код доступным на VM:
в фазах 3 и 5 нужно также убрать его транзитивные браузерные зависимости.

Остальные имена сохраняются, если в полном перечне не указано исключение.
В частности, сохраняются `ChronosGL`, `NamedEntity`, `GeometryBuilder`,
`UniformGroup`, `Material`, `RenderProgram`, `DrawStats`, `ShaderObject`,
`ShaderVarDesc`, классы текстур и framebuffer, классы света, классы анимации,
`Keyboard`, `Mouse`, `BoneVisualizer`, загрузчики, импортёры и генераторы форм.
Сохранение имени не означает сохранения всех сигнатур: это проверяется при
реализации соответствующей фазы и в таблице миграции.

## Члены классов, которые меняют владельца

Члены, не перечисленные ниже, относятся к будущему владельцу из полного перечня.
Этот принцип определяет размещение, но не обещает автоматическую совместимость
сигнатур. Подробная проверка публичных методов, конструкторов и свойств выполняется
в фазах их изменения и при оформлении API в фазе 7.

| Сейчас | Предлагаемый путь | Причина |

## Совместимость и порядок применения

1. Сначала реализовать новые сущности и обновить внутренние зависимости в фазах
   3–6. Добавление точки входа не должно случайно подключить DOM к CPU-модулям.
2. Для переименований с сохранением смысла оставить временное имя или обёртку
   с `@Deprecated` и явной заменой. Это относится, например, к `Scene`,
   `RenderPhase`, `MeshData`, функциям загрузки геометрии и исправлениям опечаток.
   Допустимость alias проверяется по фактическим сигнатурам, а не только именам.
3. Разделение камеры, изменение иерархии узлов, неизменяемые настройки и новый
   тип цвета требуют явной миграции. Простая замена имени не сохраняет их старую
   семантику; не скрывать эти изменения за формально совместимым конструктором.
4. Удаление случайных экспортов, заглушек и перенос демонстрационных сущностей
   считать source-breaking изменениями и включить в `MIGRATION.md` для 5.0.0.
   Пока 5.0.0 отмечена как unreleased, таблица остаётся предложением до ревью.
5. Ограничивать общий экспорт в фазе 7 после подготовки замен. В фазе 8
   проверить примеры и тесты через публичные импорты.
